# Spec: Bookmarks — toggle, shelf page, drill scope

> Status: Draft · 2026-08-29
> Design of record: [docs/specs/2026-08-29-cert-drill-design.md](./2026-08-29-cert-drill-design.md)
> Backlog issue: **#10** (depends on **#2** schema, **#6** drill engine)

## Problem / Context

The app already knows what you got wrong — `QuestionProgress.state` derives it
on every answer, and the "missed" queue is free. So a second "needs work" list
would be redundant, and building one would be a mistake.

Decision **D8** is what makes bookmarks worth building: a bookmark means the
thing the app **cannot** infer. It is a deliberate act saying _revisit this_ —
most valuably on a question you answered **correctly for the wrong reason**,
which is exactly the case that quietly fails you on exam day and which no
derived signal will ever surface. That is why a bookmark carries an optional
freeform note, and why the shelf shows each question's mastery state: a
bookmarked question showing `MASTERED` is not a contradiction, it is the point.

The `Bookmark` model already exists from issue #2, and issue #6's `startRun`
already reads bookmarks to build a `scopeKind: BOOKMARKS` queue. What is
missing is everything that writes and shows them.

Issues #7 and #8 render a bookmark toggle in the drill's question meta row and
bind it to `B`. This issue supplies the component and endpoints they call.

## Goals

- Bookmark or unbookmark any question in one action, from inside a drill,
  without interrupting the run.
- Attach a short note in your own words explaining _why_ it's worth revisiting.
- See the whole shelf on one page, with each question's current mastery state.
- Drill the shelf as a scope, like any other.

## Non-Goals

- **Auto-bookmarking on a miss.** That would collapse bookmarks into the
  "missed" queue and destroy the distinction this feature exists for.
- **Folders, tags, colours, or sorting UI.** One flat shelf, newest first.
- **Cross-certification shelf.** The page is scoped to one cert (`/[cert]/bookmarks`).
- **Building the `BOOKMARKS` queue.** Issue #6 already owns scope resolution.
- **Editing question content.** Notes are the user's; the question is not.

## Requirements

### Functional

**`server/api`**

- `listBookmarks(certSlug)` — every bookmark whose question belongs to that
  cert, newest first, each joined with its question (objective, type, prompt)
  and that question's `QuestionProgress.state` (or "unseen" where no row
  exists). One query with includes — not N+1 per bookmark.
- `toggleBookmark(questionId, note?)` — creates the bookmark if absent,
  removes it if present. Supplying a `note` on an existing bookmark updates
  the note **without** removing it.
- `countBookmarks(certSlug)` — the rail/tab badge count.

**Route handlers** — thin: Zod-validate, call `server/api`, `NextResponse.json`.

| Handler                              | Purpose                                  |
| ------------------------------------ | ---------------------------------------- |
| `PUT /api/bookmarks/[questionId]`    | Create or update (idempotent), with note |
| `DELETE /api/bookmarks/[questionId]` | Remove                                   |

`PUT` is deliberately idempotent rather than a POST-toggle, so a double-tap or
a retried request cannot silently un-bookmark. The _toggle_ is a client
affordance that chooses `PUT` or `DELETE` based on current state.

- `note` is optional, trimmed, and length-capped (cap chosen at plan time);
  an empty string after trimming stores `null`, not `""`.
- Both handlers return **404** for an unknown `questionId`.
- `DELETE` on a question that is not bookmarked returns **204**, not an error —
  the desired end state is already true.

**`BookmarkToggle` client component**

- `'use client'` (it has a click handler and optimistic state).
- Renders a bookmark glyph, filled and amber when set, outline and muted when
  not; `aria-pressed` reflects state and the accessible name changes between
  "Bookmark for revision" and "Bookmarked for revision".
- Optimistic: flips immediately, reverts on a failed request.
- Bound to `B` inside the drill (issues #7, #8), without stealing the key while
  a fill-in input has focus.

**Bookmarks page** — `/[cert]/bookmarks`, a Server Component (Screen 06 of the
mockup).

- Header: total count and how many are already mastered
  (e.g. "23 questions saved for revision · 11 already mastered").
- A primary action **"Drill all N →"** that starts a run with
  `scopeKind: BOOKMARKS` via issue #6's endpoint.
- One row per bookmark: objective code, question type, a mastery-state chip
  (`MASTERED` green / `SHAKY` amber / `WRONG` red / unseen muted), the question
  prompt with its inline code rendered, the note when present, and a **Remove**
  action.
- Empty state: explains what a bookmark is for and how to make one — not a bare
  "No bookmarks".
- Rail gains a `Bookmarked` entry with the count; mobile gains the `Saved` tab.

**Responsive** — required in this issue, not deferred. On phones the row
collapses to state chip + prompt + note with Remove reachable, the "Drill all"
action pins to the thumb zone, and the bottom tab bar carries `Saved`.

### Constraints

- Feature UI lives in `features/bookmarks/client/components/` — **never** in
  `src/components/`.
- `'use client'` only on `BookmarkToggle` and any other genuinely interactive
  leaf; the page itself stays a Server Component.
- Zod schemas in `features/bookmarks/schemas/`, validating at the route
  boundary only.
- `server/api` begins with `const db = await getPrismaClient()`; returns
  `ResultAsync` via `catchAsyncError`; handlers wrapped in `withRequestLogging`.
- Mastery-state chip variants via **CVA**, co-exported as `<Name>Variants`.
- Root elements carry `data-slot` (`bookmark-toggle`, `bookmark-row`).
- Colours from theme tokens only — no raw hex in a component. The mastery chip
  reuses the `--success` / amber / `--destructive` tokens from issue #1.
- Geist Mono for objective codes and inline code; Geist Sans for prose.
- Named exports only (except the Next.js page default); no `any`.
- The prompt's inline-code rendering reuses issue #7's renderer — it must not
  be reimplemented here, and must not introduce an injection vector.
- **No unnecessary comments.** Per `.claude/rules/principles.md`, comments
  explain _why_, never _what_ — the code already says what it does. Do not add
  section banners, `// Step 1:` sequences, a line that restates the line below
  it, or JSDoc that repeats a signature the types already carry. A comment
  earns its place only for a non-obvious invariant, a subtle ordering, or a
  decision whose reasoning is invisible in the code, and it stays to one line
  wherever possible. If the _why_ needs a paragraph, the design is too complex
  — simplify it instead of explaining it.

## Acceptance Criteria

Server criteria are verifiable by request against a dev server with the fixture
seeded; UI criteria through Playwright.

- [ ] `PUT /api/bookmarks/<id>` on an unbookmarked question returns **2xx** and
      creates exactly one `Bookmark` row.
- [ ] Calling that same `PUT` a second time still returns **2xx** and the
      `Bookmark` count for that question stays at **1** — it does not toggle off.
- [ ] `PUT` with `{ "note": "isolate ≠ set-default" }` on an already-bookmarked
      question updates the note and the bookmark still exists.
- [ ] `PUT` with `{ "note": "   " }` stores `null`, not a whitespace string.
- [ ] `PUT` with a note exceeding the cap returns **400**.
- [ ] `PUT` or `DELETE` with an unknown `questionId` returns **404**.
- [ ] `DELETE` on a question that is not bookmarked returns **204**.
- [ ] `listBookmarks` returns rows carrying each question's mastery state, and
      a question with no `QuestionProgress` row is reported as unseen rather
      than omitted or crashing.
- [ ] The bookmarks page renders a row for every bookmark, newest first.
- [ ] A bookmarked question whose state is `MASTERED` **is shown**, with a
      success-toned chip — it is not filtered out.
- [ ] A bookmark with a note renders that note; one without renders no empty
      note element.
- [ ] With zero bookmarks, the page renders its explanatory empty state and the
      "Drill all" action is absent or disabled — it never starts an empty run.
- [ ] "Drill all N →" issues `POST /api/drill/runs` with
      `scopeKind: "BOOKMARKS"` and navigates to the returned run.
- [ ] Clicking the toggle in a drill flips it immediately (optimistic) and it
      remains flipped after a reload.
- [ ] With the request forced to fail, the toggle reverts to its prior state
      rather than showing a false positive.
- [ ] Pressing `B` in a drill toggles the bookmark; typing `b` into a fill-in
      input types the character and does **not** toggle.
- [ ] The toggle exposes `aria-pressed` matching its state, and its accessible
      name distinguishes bookmarked from not.
- [ ] At a 390px viewport the page shows no horizontal scroll, the `Saved` tab
      is present, and "Drill all" is reachable in the thumb zone.
- [ ] `bun run check-types`, `bun run check-format`, and
      `bunx react-doctor@latest --verbose --scope changed` all pass.

## Open Questions / Risks

- **Note editing UX is unspecified.** The API supports updating a note; whether
  the shelf offers inline editing or the note is only set from the drill is a
  plan-time decision. The mockup shows notes read-only on the shelf.
- **No user scoping.** Per **D2** there is no user concept, so any visitor who
  reaches the site can mutate bookmarks. This is acceptable _only_ because the
  site is locked at the Amplify edge — that lock is a human-only infra task and
  is **not** part of this issue.
- **Cascade behaviour.** `Bookmark` cascades on question delete. Re-seeding
  that recreated question rows with new ids would orphan bookmarks; issue #3's
  upsert-on-`(exam.code, number)` is what prevents this, and this issue depends
  on that holding.
- **Count freshness.** The rail badge is rendered server-side; after an
  optimistic toggle in a drill it can be stale until navigation. Whether to
  revalidate immediately is a plan-time call.
